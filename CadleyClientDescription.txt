# MASTER PROMPT — PURXIY-INSPIRED MINECRAFT CLIENT

## PROJECT OBJECTIVE

Act as a senior Minecraft client developer, Java engineer, Fabric modding specialist, UI/UX designer, graphics programmer, and software quality engineer.

Build a polished, modular, Purxiy-inspired Minecraft client with a distinctive interface, advanced customization, smooth animations, combat and player-awareness utilities, world-rendering effects, cosmetics, HUD components, configuration management, and reliable performance.

The objective is to create an original, production-quality client inspired by the design language and feature categories of modern Minecraft clients, not to copy proprietary source code or assets.

The result must be a working software project, not merely a mockup, concept, or collection of disconnected code snippets.

## 1. PROJECT ARCHITECTURE AND TECHNOLOGY

Use a maintainable, modular architecture.

- Language: Java.
- Mod loader: Fabric.
- Build system: Gradle with the Fabric Loom plugin.
- Rendering: Minecraft's supported rendering APIs, with appropriate compatibility abstractions.
- Interface: A custom ClickGUI with reusable components.
- Configuration: Validated JSON or another suitable structured format.
- Versioning: Explicitly define the supported Minecraft version, Java version, Fabric Loader version, Fabric API version, and compatible rendering dependencies before implementation.
- Dependencies: Pin compatible versions where practical and document all required dependencies.

Organize the project into clearly separated packages for:

1. Client initialization.
2. Module registration and lifecycle.
3. Settings and configuration.
4. ClickGUI and interface components.
5. HUD and overlays.
6. Rendering and visual effects.
7. Combat utilities.
8. Player awareness.
9. World information.
10. Cosmetics.
11. External integrations.
12. Input handling and keybinds.
13. Resource management.
14. Logging, diagnostics, and testing.

Avoid monolithic classes, duplicated logic, unnecessary mixins, and undocumented global state.

Use mixins only when necessary and keep them narrowly scoped. Follow the target Minecraft version's supported APIs and conventions.

- A configurable keybind.
- Typed settings.
- A description.

- Combat
- Player
- Movement

- World
- HUD
- Utility
- Cosmetics

Provide consistent APIs for registering modules, querying their state, accessing settings, and responding to lifecycle events.

### Bokeh effect

Implement a configurable bokeh effect as a distinct visual module.

Bokeh refers to the aesthetic appearance of out-of-focus light sources and highlights, commonly represented by soft, blurred circles or polygonal highlights.

The effect should support, where technically feasible:

- Adjustable intensity.
- Highlight size.
- Blur strength.
- Density.
- Color tint.
- Opacity.
- Quality presets.
- Enable and disable controls.

Use an appropriate rendering pipeline for the target Minecraft version.

If the effect requires framebuffers, shaders, or post-processing support, implement the required resources and handle unsupported rendering configurations gracefully.

Do not label a simple collection of unblurred particles as a complete bokeh implementation.

Restore rendering state after drawing, and release GPU resources during resource reloads, world transitions, and module shutdown.

### Eight custom sky presets

Implement eight distinct sky presets:

1. **Clear Day** — bright, clean daytime atmosphere.
2. **Sunset** — warm orange, pink, and purple tones.
3. **Night** — dark sky with subtle celestial highlights.
4. **Galaxy** — deep-space colors with stars and nebula-inspired details.
5. **Nebula** — colorful atmospheric gradients and soft clouds of color.
6. **Aurora** — flowing, luminous northern-light-inspired patterns.
7. **Dream** — soft pastel colors and atmospheric gradients.
8. **Void** — minimal, dark, high-contrast atmosphere.

Each preset must have a distinct visual identity rather than being a simple recoloring of the same effect.

Where practical, provide settings for:

- Preset selection.
- Color adjustment.
- Intensity.
- Animation speed.
- Star density.
- Opacity.
- Quality.
- Optional secondary effects.

Use appropriate rendering hooks for the supported Minecraft version. Do not assume that every version exposes identical sky-rendering functionality.

If a preset requires shaders or custom resources, document those dependencies and provide a fallback when the required rendering path is unavailable.

## 14. REALISTIC DEVELOPMENT AND QUALITY CONTROL

Follow a disciplined software development process.

### Stage 1 — Requirements and feasibility

Before implementing a feature, define its purpose, expected behavior, dependencies, rendering requirements, and technical limitations.

Verify that the requested functionality is feasible for the selected Minecraft version, Fabric APIs, and supported rendering environment.

Identify any feature that requires unavailable APIs, external services, unsupported shaders, server cooperation, or additional permissions.

Do not promise unsupported functionality.

### Stage 2 — Architecture and planning

Design the required classes, interfaces, module lifecycle, settings, configuration format, and resource ownership before implementation.

Keep responsibilities separated and reuse established abstractions.

Avoid duplicated code, oversized classes, circular dependencies, unnecessary mixins, and premature optimization.

### Stage 3 — Incremental implementation

Implement one coherent feature or subsystem at a time.

For each stage:

1. Identify the files to create or modify.
2. Implement the required functionality.
3. Verify imports, types, method signatures, and dependency compatibility.
4. Run the applicable build and tests.
5. Fix identified errors.
6. Record the implementation status and remaining limitations.

Do not build large collections of interdependent features without intermediate verification.

### Stage 4 — Integration

Verify that the new implementation integrates correctly with existing modules, GUI components, settings, keybinds, configuration persistence, and rendering systems.

Check that module registration occurs once and that module state remains consistent between the GUI, keybind manager, and configuration system.

Ensure that failure in an optional feature does not unnecessarily disable unrelated functionality.

### Stage 5 — Verification

Test both normal behavior and failure cases.

Where relevant, verify:

- Valid and invalid configuration files.
- Missing resources.
- Duplicate module identifiers.
- Conflicting keybinds.
- Disabled modules.
- World changes.
- Resource reloads.
- GUI opening and closing.
- Shader compilation failures.
- Unsupported rendering features.
- External integration failures.
- Cleanup after exceptions.

Distinguish static code inspection from compilation, automated tests, and actual in-game testing.

### Stage 6 — Optimization

Measure performance before making claims about efficiency.

Profile rendering, entity iteration, configuration operations, animation updates, and external integrations where relevant.

Reduce unnecessary allocations, repeated resource creation, redundant calculations, and expensive operations on the main game thread.

Use caching only where it improves measured performance without introducing stale data or excessive complexity.

### Stage 7 — Final review

Review the completed implementation for correctness, maintainability, security, resource cleanup, dependency compatibility, and documentation.

Report the exact build and test results available in the environment.

Identify untested behavior and known issues explicitly.

### Mandatory development rules

- Never claim that a feature works merely because its code has been written.
- Never claim that the project compiles unless a build has actually completed successfully.
- Never claim that an in-game feature has been tested unless it has been exercised in the game.
- Never hide compiler errors, failing tests, missing dependencies, or unresolved implementation gaps.
- Never replace a required implementation with a placeholder without clearly identifying it.
- Never invent test results, performance measurements, compatibility claims, or build logs.
- Keep the project buildable after each significant implementation stage whenever practical.
- Prefer small, verifiable changes over large, unverified rewrites.
- When blocked, explain the precise cause, its impact, and the next feasible action.
- Preserve existing working functionality when modifying the project.

## 15. PROFESSIONAL TESTING, PERFORMANCE, AND SECURITY

### Automated Testing

- Create automated unit tests for module registration, typed settings, configuration serialization, keybind conflicts, and data validation.
- Add integration tests for configuration loading, saving, importing, and exporting.
- Run Gradle compilation and tests after every significant implementation stage.
- Fix all identified errors before marking a stage complete.

### Performance Targets

- Aim for minimal overhead when modules are disabled.
- Target less than 1 ms of additional CPU time per frame for lightweight HUD and module-management operations on the defined reference system.
- Profile expensive rendering effects and provide Low, Medium, and High quality presets.
- Avoid unnecessary allocations, repeated resource creation, blocking operations, and unbounded particle collections.
- Measure actual frame times and memory usage; never claim performance targets have been achieved without measurements.

### Crash Recovery and Reliability

- Handle malformed configuration files, missing resources, shader compilation failures, and unsupported rendering features safely.
- Preserve valid settings when configuration loading fails.
- Restore rendering state, camera state, and temporary modifications when modules disable or errors occur.
- Release GPU resources correctly during world changes, screen changes, and resource reloads.
- Log actionable error messages without flooding the log.

### Multiplayer Compatibility

- Test in single-player and on compatible multiplayer servers.
- Verify behaviour with supported Fabric API versions and test Sodium and Iris separately where feasible.
- Respect server authority: client-side visuals must never be described as server-side changes.
- Avoid sending unexpected packets, bypassing server permissions, or interfering with normal multiplayer functionality.
- Document server-specific restrictions and features that cannot be reliably detected from client-visible information.

### Security

- Validate imported configuration files and reject invalid values, excessive data, and unsafe resource references.
- Never store account passwords, OAuth client secrets, or access tokens in plaintext configuration files.
- Use authorised authentication flows for external integrations and handle expired credentials securely.
- Do not download or execute untrusted code or configuration-supplied scripts.
- Keep dependencies version-pinned where practical and document known security concerns.

### Verification Standard

Every feature must have:

1. A defined expected behaviour and acceptance criteria.
2. A documented implementation and its dependencies.
3. A reproducible test procedure.
4. Recorded test results and known limitations.
5. A truthful status: IMPLEMENTED AND TESTED, IMPLEMENTED BUT NOT TESTED, PARTIALLY IMPLEMENTED, or NOT IMPLEMENTED.

Never mark a feature as tested merely because the project compiles.

### Final Release Gate

Before release, verify that the client builds successfully, launches without fatal errors, opens and closes the ClickGUI, responds to inputs, persists settings across restarts, and cleans up resources correctly.

Provide build logs or test summaries where available, a list of known issues, exact supported dependency versions, and installation instructions.

If a requirement cannot be tested in the available environment, explicitly identify it as unverified rather than claiming success.
